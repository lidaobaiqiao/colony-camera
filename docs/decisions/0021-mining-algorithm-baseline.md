# 0021：挖掘算法基线（性质、目标与可推翻清单）

日期：2026-10-06。状态：**采用**。版本：1.7.0 之后，替代决策 0019 中的算法部分。

本决策的写法与其它 ADR 不同：**前面的 ADR 记录"我们做了什么"，本决策记录"必须成立什么、可以推翻什么"。**

写作动机：0019 及 `AGENTS.md` 第 32 行把 1.6.2 一轮 bug 修复的**具体手段**（游标、续派排序、预算分帧、0.1 格容差）写成了长期原则。后续协作者读到这些原则后只能做局部修补，无法改变架构，于是挖掘行为的根本问题（多工人开采立体的效率）始终没有被提出。本决策把**性质**与**实现选择**分开：性质永久有效，实现选择允许推翻。

---

## 一、目标函数（本决策的最重要一节）

挖掘任务的评价标准，在此之前从未被写下来。这是所有后续工作的前置定义。

**输入**

- 区域 $R$：一次立体选区产生的方块集合，含空气
- 每块 $b$ 的挖掘度 $d(b)$：空气 $0$、草/树叶等植物 $1$、泥土/树木 $2$、石头 $3$、深板岩等 $4$
- $d(b) = 0$ 的方块无需挖掘，不进入契约
- 工人集合 $W$，每名工人有挖掘等级、可用工具材质、当前位置

**输出**

- 一个"谁在何时挖哪一块"的调度

**优化目标（按优先级）**

1. **完工时间最短**：$\min \max_{w \in W} T(w)$，$T(w)$ 是工人 $w$ 完成其全部分配的时刻
2. **次优目标**：在完工时间相近时，减少工人总移动距离
3. **约束内目标**：不违反第二节的性质清单

**验收判据（必须有可执行的对照）**

- 基准场景：$8 \times 4 \times 8$ 全石头（256 块）、3 名工人、初始位于区域南侧外部、每人一把石镐
- 对照基线：1.6.2 的贪心排序实现（`MiningService.assign` 的四键排序 + 游标续扫）
- 通过条件：**同等条件下完工 tick 数不高于基线的 60%**；且性质清单全部成立
- 可扩展场景：$16 \times 16 \times 16$（4096 块）单工人 / 三工人 / 八工人，用于观察随工人数的加速比

> 为什么不写"更快就行"：不可测的目标等于没有目标。基线必须是指定版本的真实实现，结果必须是一个可复现的数字。

**关于"挖掘度"的说明**

本文档使用"挖掘度 1/2/3/4"作为**设计层的抽象刻度**。它与引擎实际值的关系需要在实现时明确映射：原版 `BlockState.getDestroySpeed` 返回秒量级的硬度，`getDestroyProgress` 返回每 tick 的破坏进度，两者都是浮点且受工具、附魔、状态影响。设计层的 1–4 只用于排序与分组决策，**不能替代引擎的真实破坏判定**——真实破坏仍必须走原版 `ServerPlayerGameMode.destroyBlock`。

## 二、性质清单（必须永久成立）

这一节的内容**任何实现都不允许违反**。它们不规定数据结构、不规定算法，只规定结果。

### P1 世界安全

- 改变世界、扣材料、破坏方块必须由服务端校验与执行；客户端只提交意图
- 不传送工人、不穿墙、不强制加载区块
- 不覆盖存在冲突的方块；不破坏方块实体、液体与不可破坏方块
- 保留 Forge 保护事件、真实掉落、经验与耐久回调

### P2 玩家意图与权限

- 挖掘目标的精确方块状态在受理时保存，执行前复查；被玩家替换或移除的成员跳过且不加经验
- 破坏前复核归属与交互权限（`mayInteract`、世界边界、维度高度）
- 区域外的方块永不被处理

### P3 挖掘的真实性

- 使用原版生存破坏管线，保留工具材质门槛与耐久消耗
- 每成功破坏一块恰好加一次挖掘经验
- 工人必须持有正确工具才能挖需要工具的方块；工具从真实来源领取
- 规划与执行使用**同一真实眼高**；粗略到位半径不代替视线检查
- 视线被遮挡时必须实际换位，不能隔着方块破坏

### P4 进度守恒

- 一块方块的破坏进度**不得因调度、换位、其他工人介入而丢失或重复计算**
- 同一块方块同一时刻**不得被两名工人同时认领**
- 任务的完成计数与实际破坏数必须守恒

> P4 是性质，不是机制。1.6.2 用"续派排序 + 每工人游标"实现它，那是实现选择（见第三节）。任何新的实现只要保证进度不丢、目标不重复认领即可。

### P5 站位的物理正确性

- 站位必须有坚实支撑、身体无碰撞、头部无液体
- 不允许破坏工人自己正在站立或依赖的支撑方块（先离开再挖）
- 浅水可作站位（脚部水、头部干），深水与熔岩不可

### P6 引擎机制不被打断

- 同一目标的活动中路线直接续行，不重复调用 `moveTo`（重复调用会重置原版卡住计时）
- 终点必须真正到达作业格中心，不允许提前结束导致来回反复
- 保留原版垂直跟进、绕角与卡住检测

### P7 导航隔离

- 可达性探查必须使用独立的规划导航器，不得修改正在执行的导航器的路线、目标或卡住计时
- 所有路线限制在已加载区域

### P8 数据完整性

- 存档格式变更必须引入 `schemaVersion` 并定义迁移
- 未知或损坏的数据进入只读保护并原样保留，不得丢弃玩家数据

### P9 持料归属

- 工人主手的物品是**真实运输库存**，不是虚拟数量
- 持料的任务归属仅用于跨任务协调；归属不移动物品、不代替预约账本
- 取消或孤立的持料允许清扫入仓，不得凭空删除

## 三、上一版实现选择（允许推翻）

以下内容来自决策 0019 与 `AGENTS.md` 第 32 行。它们是 **1.6.2 的实现选择**，不是原则。新的挖掘算法**可以整体替换它们**，只需保证第二节的性质成立。

| 编号 | 1.6.2 的实现选择 | 允许推翻的理由 |
| --- | --- | --- |
| I1 | 挖掘排序 = 高层优先 → 同层就近 → 固定 X → 固定 Z 的四键贪心 | 贪心排序把一个**空间划分**问题当成**线性排序**问题处理，是多工人效率低下的根因 |
| I2 | 游标续扫：`miningCursors` 每工人保存原始目标索引，按实际检查数量推进 | 该机制是为配合 I1 的全局排序而存在；若不再使用全局排序，游标本身失去意义 |
| I3 | 预算分帧扫描：`MAX_PATHS = 16`、dispatch 期间 `40`、每工程至多 `16` | 预算模式是对"每次扫描都要寻路"的补偿。新架构若按站位聚合，寻路次数本就大幅下降 |
| I4 | 续派优先：`workTask.deadline >= time ? 0 : 1` 决定工人遍历顺序 | P4 要求的是"进度不丢、不重复认领"，续派排序只是达成手段之一 |
| I5 | 站位由"目标块"反查：`findStand(level, worker, target, ...)` | 签名方向反了。正确形态是先定站位、再问覆盖哪些块（见第四节） |
| I6 | 站位搜索半径：挖掘 `dy∈[-2,1]`、曼哈顿 `\|dx\|+\|dz\| ≤ 3`；施工 `dy∈[-1,1]`、`≤ 3` | 这是 magic number 组合，与架构绑定；新架构应按暴露面生成候选站位 |
| I7 | 终点水平容差固定 0.1 格（`dx*dx+dz*dz > 0.01` 则重走） | P6 要求的是"真正到达格中心"，0.1 只是当时的取值。**保留该测试，允许调整数值** |
| I8 | 单块挖掘进度上限 `FINISHED_PROGRESS = 10_000`，增量按 `perTick * 10000` 取整并乘 `elapsed`（夹在 0–5） | 进度表示形式可以改；P4 只要求守恒与不重复 |
| I9 | 挖掘技能阈值 `{0,16,48,112,240}` → 等级 1–5，每级 +15% 速度 | 数值平衡可调；等级机制本身属于玩法范围，不在此决策内 |
| I10 | 目标任务列表上限 64 项扫描、`MIN(64, size)` 循环 | 与 I3 同源，属于预算模式的产物 |

**推翻 I1–I10 不需要修改 `AGENTS.md`**，因为本决策同时把 `AGENTS.md` 第 32 行中描述这些实现选择的句子移出（见第六节）。

## 四、推荐的目标形态（非强制）

本节是**建议**，不是约束。给出它是为了说明"性质可以如何被更好地满足"，而不是规定唯一实现。

### 4.1 核心转变

> 挖掘不是"选下一块挖什么"，而是"选下一段从哪挖、按什么方向推进"。
> **站位是主变量，方块顺序是副变量。**

理由：工人移动的时间成本远大于单块挖掘时间（走 10 格约 50 tick，挖一块石头约 30 tick）。**移动才是稀缺资源**，因此优化对象应当是"减少移动次数"，而非"优化挖掘顺序"。

### 4.2 分层剥离（替代 I1）

- 计算每块的暴露面数（6 邻居中空气/已清空的数量）
- 只处理"暴露面 ≥ 1"的前沿集合
- 按"多暴露面优先 → 上层优先 → 软质优先 → 就近"推进
- 每挖掉一块，增量更新邻居的暴露面计数（$O(1)$ 均摊）

效果：工人在已清空区域或区域外沿作业，视线永远畅通，掉落物落在台阶上。**天然实现"从上往下 + 从外向内"**。

### 4.3 站位池与覆盖集合（替代 I5/I6）

- 每个前沿块按其暴露面生成 1–3 个候选站位（正对暴露面优先，斜 45° 次之）
- 每个站位计算覆盖集合 $C(s) = \{b : s \text{ 能挖到 } b\}$
- 站位价值 = 覆盖价值 × 独占性 × 距离惩罚
- 工人一次寻路可连续开采 $C(s)$ 中的多块

### 4.4 扇区划分（替代 I4）

- 把前沿按连通分量分解，每个分量在长边方向等分为 $|W|$ 个扇区
- 硬活（高挖掘度、需要高级工具）优先分给高等级工人
- 负载预测 + **滞回阈值**：仅当两名工人预测负载差超过阈值时才重分配，避免频繁掉头

> 注意：滞回阈值是本节的关键设计。没有它，负载均衡会把"多挖两块"的收益换成"多走两趟"的代价。

### 4.5 进度绑定在方块上（强化 P4）

建议把进度从 `WorkTask`（瞬态）迁移为按方块位置索引的持久结构，使进度可以**跨站位、跨任务、跨工人**保留。这样一块挖了 70% 的深板岩在工人被临时调走后仍保留 70%。

### 4.6 动态增量更新

- 前沿集合增量维护，不每 tick 重算全局
- 只在以下情况重规划：前沿变化、扇区完成、工人阻塞超过 N tick、新任务介入
- 其他时间走局部执行（工人只关心自己扇区的下一块）

### 4.7 需要单独判断的分支

**水下区域不能沿用"从上往下"**：水会流入已挖空间，把工作面灌满。此情形需要改为"从边缘向中心挖 + 及时排水"，或提示玩家先行排水。这是必须在实现时明确处理的分支，不能默认套用陆地策略。

## 六、`AGENTS.md` 的相应调整

本决策生效后，`AGENTS.md` 应只保留**性质级**描述。具体建议：

**第 32 行现状**（一段混合了 D1–D10 性质与实现的长句）应拆分为两部分：

- 保留：P3（真实眼高、视线检查）、P4（进度守恒、不重复认领）、P5（不挖自己支撑）、P6（续行、终点精度）、P7（导航隔离）的**性质表述**
- 移出：I1–I10 的**实现细节**（四键排序、游标机制、预算数值、站位搜索半径常量），改为指向本决策

**判断标准**：如果一句话描述的是"必须成立的结果"，留在 `AGENTS.md`；如果描述的是"用某某数据结构实现"，移入本决策第三、四节。

**推荐在新版本号内一次性完成这次调整**，避免 `AGENTS.md` 与 ADR 长期处于描述冲突的状态。

## 八、边界

本决策**只定义挖掘算法**。不涉及：施工放置、清扫、合成、研究、仓储网络、科技树、UI。这些模块的约束维持原状。

本决策**不改变**任何存档格式、网络协议或模式 ID。第一节的目标函数与第三节的推翻清单都不需要落盘。

本决策**不承诺**自动修路、搭桥、深水潜泳、脚手架或任何超出"在已达到的站位上挖到规定区域方块"的能力。
