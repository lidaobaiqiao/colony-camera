# 0022：建造算法基线（脚手架模型、性质与目标）

日期：2026-10-06。状态：**采用**。适用范围：施工（ConstructionProject）的全部工人行为。

与 [0021](0021-mining-algorithm-baseline.md) 同规格：本文件写"必须成立什么、可以推翻什么"，不规定具体数据结构。
0021 管挖掘，本文件管建造。两者共用"空间调度"框架，但**约束方向相反**（挖掘自上而下，建造自下而上）。

---

## 一、核心模型：工人是打印头，脚手架是导轨

**这个模型来自用户，是本文件所有设计的基础。**

> 建造如同 3D 打印：建筑是要打印的实体，工人是打印头，**脚手架是打印头的导轨/龙门架**。
> 交互距离是打印头的机械臂长度；脚手架保证机械臂够得到所有作业面。

三个角色：

| 3D 打印 | Minecraft | 说明 |
| --- | --- | --- |
| 打印机身 / 龙门架 | **脚手架** | 提供站位与竖直移动通道 |
| 机械臂长度 | **交互距离** | 工人能触及的范围 |
| 支撑材 | **内脚手架** | 跨度超出交互距离时的中间支撑 |
| 逐层堆叠 | **逐层建造** | 自下而上 |
| 拆除支撑材 | **拆脚手架** | 完工后拆除 |
| 打印头路径 | **工人移动路径** | 覆盖所有待放位置 |

**为什么这个模型是对的**：原版脚手架（Scaffolding）的设计意图本来就是"building structures / help the player reach higher places"。工人用它，是原版机制的正统用法，不是外挂。

## 二、脚手架类型（三种，均为独立方块）

用户确定：原版脚手架配方不变；新增泥土与石头两种，构成成本梯度。

| | 原版脚手架 `minecraft:scaffolding` | 泥土脚手架 | 石头脚手架 |
| --- | --- | --- | --- |
| 配方 | 6 竹子 + 1 线 → 6 个 | **7 泥土 → 1 个** | **7 石头 → 1 个** |
| 挖掘速度 | 瞬间 | 快 | **慢**（需工具） |
| 无工具挖掘 | 可以 | 可以 | **不掉落任何东西** |
| 掉落 | 掉落自身（可回收） | **只掉 1 个泥土，不掉落脚手架** | 掉落自身（可回收） |
| 定位 | 标准 | 一次性、最廉价 | 前期投入、可回收 |

**三种都保持原版脚手架的全部行为**：可攀爬（跳跃上 / 潜行下）、无碰撞判定（仅在持有脚手架时顶面为完整碰撞）、横向延伸上限 6 格、底部拆除整柱崩塌。这是本设计的硬前提——任何一条不成立，模型即失效。

**泥土脚手架是材料损耗项**：7 泥土 → 回收 1 泥土，净损耗 6/7。这是有意为之的取舍（泥土近乎无限，用资源换时间）。

**实现提示（允许推翻）**：制作方块的掉落表可用 `LootTableProvider` 分别定义；"无工具不掉落"用 `requiresCorrectToolForDrops` + 石头脚手架设 `needs_iron_tool` 或类似的 tier 门槛实现。掉落数量 1 可调。

## 三、脚手架启用与布置规则（用户确定）

### 3.1 启用条件：只有高度达标才启用

```
建筑最大高度 < 阈值  →  不启用脚手架，工人站在地面上作业
建筑最大高度 ≥ 阈值  →  启用脚手架
```

**默认阈值：3 格**（工人站在地面可舒适触及的高度；此为可调参数，非性质）。

这条规则避免了矮建筑上搭脚手架的无谓开销。

### 3.2 布置规则：单个脚手架覆盖 6×6

| 建筑 XZ 尺寸 | 脚手架布置 |
| --- | --- |
| ≤ 6 × 6 | **1 个**（单柱） |
| 长边 > 6、短边 ≤ 6 | **1 排**（沿长边，间距 ≤ 6） |
| 两边都 > 6 | **网格**（两方向间距均 ≤ 6） |

**布置是"按覆盖需求算出来的"，不是"绕建筑兜一圈"。** 这一点必须明确，否则实现会做出大量无用脚手架。

### 3.3 覆盖几何（实现时必须按精确值算，不要硬编码 6）

单柱脚手架的作业覆盖由两个量共同决定：

- **交互距离**（用户指定 **5.0**）：工人在脚手架上能触及的球形半径
- **脚手架横向延伸**（引擎强制 **6 格**）：工人可沿脚手架横向移动的范围

因此单柱的实际作业覆盖显著大于 6×6：

```
若脚手架柱位于区域中心：
  水平作业半径 = 交互距离
  工人可沿脚手架横向移动 ±6 格（但一次只能站一格）

综合覆盖：以脚手架柱为中心、半径约 5 的圆形作业面，
         叠加脚手架自身可延伸 6 格形成的"可移动轨道"
```

**精确间距公式由实现计算**，输入为交互距离、延伸上限、作业面形状（矩形/不规则）。
本文件只规定结果：**任意建筑方块必须被至少一个脚手架位置覆盖（距离 ≤ 交互距离）**。

### 3.4 内脚手架的判据

```
建筑某处方块，距离最近的外脚手架水平距离 > 交互距离
  → 该处必须搭内脚手架
```

内脚手架同样遵循横向延伸 ≤ 6 的规则。

## 四、目标函数（建造版）

### 输入

- 建筑方块集合 $B$（来自投影，已单元分解）
- 每块 $b$ 的放置成本 $\text{place}(b)$：与其 `canSurvive` 约束、依附关系有关
- 脚手架规划 $S$：外脚手架 + 内脚手架（按第三节规则生成）
- 材料清单 $M$：建筑材料的真实物品账单 + 脚手架材料
- 工人集合 $W$，各自属性（速度、建造技能、可用工具、携带容量）

### 输出

- 一个"谁在何时何站位放置/拆除哪个单元"的调度

### 优化目标（按优先级）

1. **完工时间最短**：$\min \max_{w} T(w)$，含脚手架搭拆的完整时间
2. **材料损耗最小**：泥土脚手架的净损耗与重复搭建次数
3. **移动距离最小**：工人在脚手架与仓储间的往返

### 验收判据

- **基准场景 A（无脚手架）**：4×4×3 实心石屋，2 工人，材料就位 → 记录完工 tick
- **基准场景 B（单柱脚手架）**：6×6×6 中空石屋，2 工人 → 脚手架应为 1 个柱
- **基准场景 C（网格脚手架）**：12×12×6 中空石屋，3 工人 → 脚手架应为网格
- **对照基线**：1.7.0 的现有实现（`ConstructionManager.findStand` + 逐块建）
- **通过条件**：A/B/C 三场景完工 tick 不高于基线 **60%**；且第二节性质全部成立

> 基线数字必须在动手前实测记录，否则目标不可验证。

## 五、性质清单（必须永久成立）

### P1 世界安全
- 改变世界、扣材料、执行放置与拆除必须由服务端校验与执行
- 不传送工人、不穿墙、不强制加载区块
- 保留 Forge 放置/破坏保护事件与真实掉落

### P2 材料守恒
- 建筑材料与脚手架材料都来自真实库存，不得凭空生成
- 放置成功后才消耗携带物品；拆除的脚手架按各自掉落规则回收
- 泥土脚手架的材料损耗是**规则内的预期行为**，不是 bug

### P3 支撑正确
- 放置前复查 `canSurvive`；不满足则延后而不是强行放置
- 不使用投影中不存在的方块做支撑（脚手架除外）

### P4 站位物理正确
- 工人不能站在自己即将放置的方块位置上
- 站位需要坚实支撑、身体无碰撞、头部空间合法
- 在脚手架上：顶面可行走，竖直方向用原版攀爬

### P5 不封死自己
- 任何时刻，工人必须存在一条可达路径离开施工区域
- 对封闭倾向的投影（房间、隧道、包围结构），必须识别并处理"出入口最后放"

### P6 依赖顺序
- 支撑依赖、依附依赖（火把/门）、单元原子性（门/床/半砖）必须成立
- **特殊方块（画、展示框、告示牌等需依附面的）在主体完成后单独处理**

### P7 拆除安全
- 拆除脚手架不得误伤建筑方块
- 内脚手架的拆除必须保证工人有站位（见 6.3）
- 原版脚手架的底部崩塌特性可利用（一次拆整柱）

### P8 进度守恒
- 单元的放置进度不得因调度、换位、他人介入而丢失或重复计算
- 同一单元同一时刻不得被两名工人同时认领

### P9 引擎机制不被打断
- 同目标的活动路线直接续行，不重复调用 moveTo
- 终点真正到达作业站位中心
- 保留原版垂直跟进、绕角与卡住检测

### P10 导航隔离
- 可达性探查使用独立规划导航器，不修改执行导航器的路线与卡住计时
- **规划导航器必须把脚手架识别为可通行 + 可攀爬**（否则工人不会走上脚手架）

### P11 数据完整性
- 存档格式变更引入 schemaVersion 并定义迁移
- 未知或损坏数据进入只读保护并原样保留

## 六、算法设计（推荐形态，非强制）

### 6.1 阶段 0：投影预分析（工程创建时执行一次）

```
① 单元分解（沿用现有 BuildPlan）
② 高度检查 → 决定是否启用脚手架
③ 外脚手架规划
     按 3.2 规则生成：单柱 / 一排 / 网格
     位置：建筑轮廓外，避开所有投影方块位置
     高度：建筑最大高度 + 余量（建议 +2，便于放特殊方块）
④ 内脚手架规划
     对每个建筑方块，计算到最近外脚手架的水平距离
     距离 > 交互距离 → 该处需要内脚手架，按层生成
⑤ 封死检查（P5）
     运行"逆序拆除测试"：假装已建好，从"工人在外"反推能否逐个拆除
     拆不动 → 标记必须最后放置的单元（通常是门的占位）
⑥ 特殊方块清单
     识别画/展示框/告示牌等需依附面方块 → 标记为阶段 3
⑦ 材料账单
     建筑材料（现有）+ 脚手架材料（新增）
     向玩家报告总需求
```

### 6.2 阶段 1：搭外脚手架

- 一次搭到顶（原版侧面对准放置可无限向上堆叠）
- 多工人时按柱分工，互不干扰
- 材料由工人从仓储/地面领取（沿用现有取料流程）

### 6.3 阶段 2：逐层建造

```
for 每一层 Y（从低到高）:
    ① 判断本层是否有内脚手架需求（6.1 ④ 的结果）
       有 → 先搭本层内脚手架
    ② 建造本层建筑单元
       - 站位候选：外脚手架 + 本层内脚手架
       - 单元选择：贪心 + 前瞻
           cost(u) = 从当前站位走过去 + 放置 + 材料搬运
                    - λ · 解锁数（放了 u 之后新就绪的单元数）
       - 站位避开"投影中未来的方块位置"
    ③ 拆本层内脚手架
       - 顺序：工人先上升到上一层（或外脚手架对应高度），从上往下拆
       - 若无上层可达 → 从区域外沿拆向中心，保证退路
       - 原版脚手架拆底部即整柱崩塌，可利用
```

**6.3 ③ 是施工算法最精细的一步。** 内脚手架拆不下来会导致后续无法继续（它占着上层方块的位置）。

### 6.4 阶段 3：收尾

```
① 放置特殊方块（画/展示框/告示牌）
   - 站位：外脚手架（建筑完工前不拆）
   - 依赖：识别每个特殊方块需要的依附面，按"依附面已完整"分组
② 拆外脚手架
   - 拆底部 → 整柱崩塌
   - 石质脚手架须持镐（无工具不掉落）
   - 回收到仓储
```

### 6.5 多工人扇区划分

- 沿建筑长边切分扇区，每工人一段
- **扇区边界交错**：避免两名工人争抢同一列（建议奇偶层交错）
- 脚手架是**共享轨道**，扇区是**责任田**
- 硬化单元（高支撑要求 / 特定材料）分给能力匹配的工人

### 6.6 材料流（与现有实现的关键差异）

**现状**：每单元携带 1–2 件（`unit.count()`），工人为每块材料跑一趟。

**改进**：**工人一次携带更多材料**，放一块扣一块。

理由：移动是稀缺资源（走 10 格约 50 tick，放置一块不到 10 tick）。一次带 36 块跑一趟，远优于跑 18 趟。

代价：`cargoTask` 语义变化（从"这一单元的材料"变为"这一批的材料"），且需处理"携带的材料类型与实际需求不匹配"的情况。

## 七、可推翻清单（1.7.0 的实现选择）

以下为现有实现的选择，**允许整体替换**，只需保证第五节性质成立。

| 编号 | 现有实现选择 | 允许推翻的理由 |
| --- | --- | --- |
| C1 | 站位由目标单元反查（`findStand(level, worker, unit)`，`dy∈[-1,1]`、曼哈顿 ≤3） | 签名方向反了。正确形态是先有脚手架轨道，再在轨道上选站位 |
| C2 | `project.cursor` 轮转（`(start + min(64, size)) % size`） | 与挖掘的游标同源，都是"用线性游标解空间问题" |
| C3 | 每单元携带 1–2 件（`unit.count()`） | 见 6.6，应改为批量携带 |
| C4 | 每 tick 全量遍历工人调用 `findAssignment` | 应改为就绪前沿 + 增量更新 |
| C5 | `pathBudget` 全局 40 / 每工程 16 | 预算模式是对"每单元都要寻路"的补偿；脚手架轨道建立后寻路次数大幅下降 |
| C6 | 无脚手架概念，`canReach` 直接判断 | 缺少模型基础结构，需整体新增 |
| C7 | `dropCarried` 在材料类型不匹配时直接掉落 | 批量携带后需要更细致的"部分材料不匹配"处理 |
| C8 | 工程完成=单元位图全满 | 需扩展为"建筑 + 脚手架搭拆"的完整生命周期 |

## 九、测试判据

### 9.1 新增测试

- **脚手架规划**：给定建筑尺寸与高度，验证生成的脚手架数量与位置符合 3.2/3.3
- **矮建筑不搭脚手架**：高度 < 阈值时脚手架集合为空
- **单柱覆盖**：6×6 建筑只生成 1 个脚手架
- **一排覆盖**：长条建筑生成一条排
- **网格覆盖**：两面都 > 6 时生成网格
- **覆盖完备性**：所有建筑方块距最近脚手架 ≤ 交互距离
- **逐层建造顺序**：任何时刻放置的单元其支撑已存在
- **内脚手架拆解**：拆内脚手架不误伤建筑，且工人有站位
- **封死检查**：封闭房间能正确识别出入口并最后放置
- **特殊方块延后**：画/展示框在主体完成后才放置
- **材料守恒**：泥土脚手架 7→1 损耗符合预期；石头脚手架可完整回收
- **完工时间**：A/B/C 三场景对照基线

### 9.2 保留的既有测试

- 施工的放置/回滚/保护事件测试
- 单元分解（门/床/半砖）测试
- 材料守恒与预约测试
- 端点到位、卡住检测、导航隔离测试

### 9.3 测试纪律（延续现有约定）

- 不为简单文案建立镜像测试
- 分支隔离，测试批次不互相污染
- **不得为通过测试而修改玩法或给掉落额外归属**
- 停用测试必须写明原因与跟进条件

## 十、实施顺序建议

1. **先落地三种脚手架方块**（含配方、掉落、语言、模型）——这是模型的基础设施
2. **扩展投影预分析**（高度检查 + 脚手架规划 + 覆盖完备性）
3. **导航器识别脚手架**（P10 的攀爬与可行走）
4. **重写阶段 2 的建造顺序**（就绪前沿 + 站位来自脚手架）
5. **实现内脚手架的逐层搭拆**
6. **实现阶段 3（特殊方块 + 拆外脚手架）**
7. **批量携带材料**（6.6）
8. **补齐测试 + 回填验证记录**

## 十一、边界

本文件只定义**施工的工人行为**。不涉及：挖掘（见 0021）、清扫、合成、研究、仓储网络、科技树、UI。

已明确不做：
- 自动修路/搭桥
- 破拆（拆除玩家或既有的非脚手架结构）
- 超出脚手架能力范围的复杂悬挑结构（由 `canSurvive` 自然拒绝）

需要单独确认的分支：
- **水下施工**：与挖掘同源问题，水会灌满工作面
- **脚手架与建筑的"位置冲突"**：脚手架规划必须避开投影方块位置，但若建筑本身占满外围则无法搭脚手架（需拒绝并报告）
